LocalServicePod

Expose a service running on your developer machine to in-cluster clients — without deploying a container.

LocalServicePod is not a normal "run a container in Kubernetes" pod. Its job is to expose a service already running on the developer's machine to in-cluster clients by creating Kubernetes networking resources that point back to the host machine. The workload itself lives on your laptop; the pod only provisions the Kubernetes routing layer.

What Makes It Different

Selector-less Service + Manual Endpoints

Instead of a standard workload-backed Service, LocalServicePod creates two resources manually:

  • A ClusterIP Service with no selector — Kubernetes will not attempt to route traffic to any in-cluster pods.
  • A manually managed Endpoints object whose address is set to the developer host's IP.
In-cluster caller → name.namespace.svc.cluster.local
↓ ClusterIP Service (no selector)
↓ Endpoints { ip: <host IP>, port: hostPort }
→ localhost:hostPort (your laptop)

In-cluster callers use the normal DNS name name.namespace.svc.cluster.local, but traffic is forwarded to the local machine instead of an in-cluster workload.

Port Configuration

Two Ports to Configure

You configure the bridge with exactly two port declarations:

onHostPort(…)
The port your local service listens on. Written into the Endpoints object as the target address.
exposingServicePort(…)
The port the cluster-side Service exposes to in-cluster callers.

The Service is created with port = exposingServicePort and targetPort = hostPort, and the Endpoints object carries the host IP paired with hostPort.

Startup Sequence

Host IP Resolution

On start(), after resolving cluster and namespace defaults, the pod resolves a routable host IP:

  • Prefers host.minikube.internal — the standard hostname Minikube exposes for host access.
  • Falls back to InetAddress.getLocalHost() if that hostname is not reachable.
Kubernetes Endpoints require an IP literal, not a DNS name. The resolved address is written directly into the endpoint object — not a hostname.
LocalServicePod.java:394–414

Resource Creation & Partial-Failure Cleanup

Once the host IP is resolved, two Kubernetes resources are created in order:

  • A ClusterIP Service with port = exposingServicePort, targetPort = hostPort.
  • An Endpoints object with the host IP and port = hostPort.
If creation fails partway through, the pod performs a best-effort deletion of both resources — so you are never left with a broken Service/Endpoints pair in your namespace.

Unsupported Features

Container-Oriented APIs Are Not Available

Because LocalServicePod does not schedule an in-cluster workload, container-oriented features throw at runtime:

  • withResources(…)
  • withInitContainer(…)
  • withSidecar(…)
  • withPodCustomizer(…)
  • waitingFor(…)
  • getLogs()
  • exec()

getLogs() and exec() are also unsupported because there is no in-cluster container to inspect.

Address & State Semantics

Host / Port / Readiness Methods

The accessor methods follow a consistent mapping that reflects the two-sided nature of the bridge:

Method Returns
getInternalHost() name.namespace.svc.cluster.local — the in-cluster DNS name
getInternalPort() exposingServicePort — what in-cluster callers connect to
getExternalHost() localhost — always, unconditionally
getExternalPort() hostPort — the port your local service listens on
isRunning() / isReady() Returns the started flag only — not a live pod health check
isRunning() and isReady() reflect whether the resources were successfully created, not whether the local service is actually healthy.

Testability

KubernetesGateway Seam for Unit Tests

A small KubernetesGateway interface is injected between LocalServicePod and the real Kubernetes client. This seam lets tests supply a fake gateway and assert on the exact Service and Endpoints objects that would be created — without requiring a live cluster.

This is why unit tests can verify the precise generated resource content in isolation.
