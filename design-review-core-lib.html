TestPods Core Library — Design Review

Architecture assessment and refactoring proposal for the testpods-core artifact, oriented toward a minimal, 100%-working, well-documented initial release.

Executive summary

The core idea is strong and the hard parts are largely solved. The Testcontainers-style fluent API, the strategy seams (workload / service / access / wait), the property-publishing system with dependency-ordered startup, and the minikube profile-ownership semantics are all genuinely good design. LocalServicePod (run one service on the laptop against in-cluster dependencies) is a differentiating feature Testcontainers cannot offer.

The main risks to an initial release are structural, not functional:

  • Coupling knots — a bidirectional dependency between core.provisioning and junit, the cluster package depending on the pods package, and the K8sCluster interface constructing its own MinikubeCluster implementation.
  • One fat cluster interface mixing three concerns: cluster provisioning/lifecycle, cluster connection, and namespace management — exactly the split the project owner suspects is needed. It is.
  • A 933-line BaseManagedPod carrying at least eight responsibilities, including minikube-specific image preloading that does not belong in a generic base class.
  • Roughly 25–30% of the public surface is dead, unwired, or aspirational — an entire unused storage package, placeholder Maven modules, unimplemented annotations, stub factory methods that throw, and 10 @Deprecated members in a library that has never shipped.

Recommendation: before adding any feature, run a deletion pass (Wave 1), then perform three targeted structural refactorings (Wave 2): split the cluster interface, break the junit↔core cycle, and decompose BaseManagedPod. That yields a lib whose public surface matches what actually works — the precondition for the stated motto: a small set of features that works 100%.

1. Scope & method

This review covers the testpods-core Maven module (the primary artifact, ~12,900 lines of main-source Java across 60+ classes), its relationship to the bom, modules/*, and examples/* modules, and the JUnit 5 integration in org.testpods.junit. Every class named below was read in full or in relevant part; findings cite file and line so they can be verified. The PRD (prd/) and specs (specs/) were used to calibrate intent, and the review is framed against the stated release goal: minimum feature set, tested, complete, high-quality docs.

3. Design strengths

S1 — Familiar Testcontainers mental model

Fluent pod builders, waitingFor(...), getMappedPort(...), getHost(), @TestPods/@TestPod mirroring @Testcontainers/@Container. Adoption friction for the target audience is near zero. This is the single most valuable API decision in the project — protect it.

S2 — The strategy seams already exist and demonstrably work

WorkloadManager (Deployment/StatefulSet), ServiceManager (ClusterIP/Headless/NodePort/Composite), ExternalAccessStrategy (4 impls), and WaitStrategy (6 impls) are clean, single-purpose interfaces. KafkaPod proves the seams carry real weight: it composes a StatefulSet workload with a composite service and a custom wait strategy without touching the base class. This is composition-over-inheritance done right, and it is the backbone the refactoring should build on, not replace.

S3 — PropertyContext + dependency-ordered startup is a genuine differentiator

Pods publish lazy connection properties (${postgres.internal.uri}); consumers reference them in env templates; Registry.orderInitializationsForStart() (Registry.java:133) topologically sorts pods by referenced properties and detects cycles. Wiring a multi-service slice declaratively is something Testcontainers users do by hand. Keep, document, and showcase this.

S4 — Ownership semantics are carefully thought through

Namespace.owned() vs Namespace.external() with deleteNamespace refusing to delete non-owned namespaces (MinikubeCluster.java:197); profile ownership decided at attach-vs-start time with policy downgraded to LEAVE_RUNNING when attaching (MinikubeCluster.java:97); per-profile startup locks handling concurrent JVM construction. This is the kind of safe-by-default engineering a test library must have.

S5 — LocalServicePod is a killer feature for the development use case

A selector-less Service + manual Endpoints pointing at the developer's machine, so in-cluster pods reach the locally-running (debuggable) service by normal DNS. Combined with the external kubectl port-forward access strategy that survives debugger suspension (ExternalAccessStrategy.java:195 — a subtle, well-reasoned choice), this covers the "develop one service against real deps" workflow that motivated the project.

S6 — Documentation discipline

Recent code has strong Javadoc explaining why (e.g., the profile lock comment in MinikubeCluster.java:48–55), and the repo carries PRDs, specs, and explanatory HTML pages. The raw material for high-quality release docs exists.

4. Design concerns

Ordered roughly by how much they threaten the release goal. Each cites verifiable evidence.

C1 — Coupling knots between packages and between interface and implementation High

Four distinct dependency problems compound each other:

  1. core.provisioning ↔ org.testpods.junit is a cycle. Registry imports junit.TestPodGroup; FieldDeclaration/FieldInitialization import the @TestPod annotation; ReflectionHelper imports @RegisterCluster. Meanwhile TestPodsExtension imports Registry/Provisioner. The "core" domain layer knows about its JUnit adapter and vice versa — neither can be extracted, versioned, or tested independently, and a future TestNG/Spock adapter is impossible without duplicating provisioning.
  2. The cluster package depends on the pods package. ExternalAccessStrategy.getExternalEndpoint(Pod<?>, int) (ExternalAccessStrategy.java:43) forces the cluster layer to understand the pod abstraction, creating a package-level cycle (pods also uses cluster). The strategy only actually needs namespace, service name, fixed-port hint, and a client.
  3. The K8sCluster interface constructs its own implementation. discover() calls MinikubeCluster.builder() directly (K8sCluster.java:51). An interface that news up one concrete impl can never support "multiple k8s cluster impls" cleanly — Kind/kubeconfig support would mean editing the interface.
  4. Generic pod code depends on minikube specifics. BaseManagedPod.preloadExternalImageForMinikube(...) (BaseManagedPod.java:447) imports cluster.minikube.* and does instanceof MinikubeImageLoadTarget; GenericPod.fromLocalImage throws unless the cluster is minikube (GenericPod.java:119).

Consequence: the library cannot grow the way the PRD intends (more cluster types, more framework adapters, more modules) without every addition touching the center. This is the root cause behind most other concerns.

C2 — K8sCluster mixes three responsibilities plus factory duties High

The single interface currently answers four different questions:

ConcernMembers on K8sCluster today
Cluster provisioning / lifecycle ("operate the cluster machinery")discover(), discover(policy), newMinikube(), newKind(), fromKubeconfig() ×2, close(); plus profile/policy/ownership on the impl
Connection ("talk to the API server")getClient(), getAccessStrategy()
Namespace management ("manage my workspace")getDefaultNamespace(), getNamespace(name), createNamespace() ×2, attachNamespace(), deleteNamespace()
Fluent odditywithNamespace() returning K8sCluster (K8sCluster.java:99) — a mutating builder method on a runtime interface

Additional problems within this interface:

  • newKind() and both fromKubeconfig() overloads throw UnsupportedOperationException — advertised API that fails at runtime. In an MVP whose motto is "everything shipped works", these must not exist.
  • discover() is misnamed: if no profile is running it starts one (cli.up, up to 3 minutes) with DESTROY_ON_CLOSE. Discovery with heavyweight side effects surprises users and CI.
  • Javadoc/behavior mismatch: the discover() Javadoc says it tries profile "minikit", the error message says minikube start -p minikit, but the builder default is DEFAULT_PROFILE_NAME = "testpods" (MinikubeCluster.java:30). Three profile names — minikit, minikube, testpods — circulate in docs, code, and messages.
  • getNamespace(name) returns null with a // TODO handle namespace not found (MinikubeCluster.java:157).
  • getDefaultNamespace() is mutable and surprising: every createNamespace() call silently re-points the default to the newest namespace (MinikubeCluster.java:233).

C3 — BaseManagedPod is a god class High

933 lines with at least eight distinct responsibilities:

  1. Fluent configuration state (name, labels, ports, customizers) — belongs here.
  2. Start/stop orchestration (doStart/doStop, lifecycle hooks) — belongs here.
  3. Cluster/namespace default resolution (resolveRuntimeDefaults, :839) — policy logic entangled with C6.
  4. Exec/log plumbing over Fabric8 (:249–305).
  5. External endpoint caching (mappedPorts, :340).
  6. Minikube image preloading with a static IdentityHashMap keyed by cluster instance (:88–90, 447–468) — cluster-impl-specific code in the generic base.
  7. A ~250-line debug report builder (buildDeploymentDetailsReport + six appendX helpers, :508–733) — valuable feature, wrong home.
  8. Env-var masking, label building, misc utilities.

Symptoms already visible: a commented-out duplicate field (:93), getClient() throwing ClassCastException as a "no cluster" error (:314), and start() calling resolveRuntimeDefaults() twice (once in start(), again in doStart()). Every new pod type inherits all of this whether it needs it or not.

C4 — The Pod interface is too wide (interface-segregation violation) Medium

Pod<SELF> declares ~30 methods spanning configuration, lifecycle, observability, internal/external endpoints, and property publishing. The proof it is too wide ships in the same package: LocalServicePod — a first-class feature — must implement all of it and throws UnsupportedOperationException five times (init containers, sidecars, pod customizers, resource requests, exec) because those concepts don't apply to a service-without-workload. Two default methods on the interface itself also throw (withExposedPorts, withFixedExposedPort, Pod.java:156–167). An interface where implementations must refuse parts of the contract will keep fracturing as pod kinds are added (Job pods, Helm-based pods, operator-managed pods…).

C5 — MinikubeCluster constructor does heavyweight, non-obvious work Medium

Construction performs: preflight checks → possible 3-minute profile start → client build + ping with retry → creation of a namespace (side effect: every MinikubeCluster owns a namespace you didn't ask for) → dashboard addon enablement + endpoint wait (up to 1 minute) + proxy process spawn (MinikubeCluster.java:67–104, 334–354). The dashboard is a debugging aid, yet every user — including CI — pays for it on every cluster start. Constructors that shell out, sleep, and spawn processes are also effectively untestable without a live minikube. The namespace-on-construction also partially duplicates what Registry.ensureNamespaceIsActive() and BaseManagedPod.resolveRuntimeDefaults() do, so three layers negotiate "which namespace am I in".

C6 — Configuration resolution maze with mutable static state Medium / High

A pod's cluster and namespace can come from five places: explicit inCluster()/inNamespace(Namespace); string-based inNamespace(String) resolved at start; TestPodDefaults thread-local suppliers; TestPodDefaults global suppliers; and implicit K8sCluster.discover() fallback. The resolution order lives partly in TestPodDefaults and partly in BaseManagedPod.resolveRuntimeDefaults(). Static mutable state is spread over four homes: TestPodDefaults (InheritableThreadLocal + globals), BaseManagedPod.PRELOADED_MINIKUBE_IMAGES, GenericPod.LOADED_LOCAL_IMAGES, and MinikubeCluster.PROFILE_STARTUP_LOCKS. This makes behavior dependent on invocation history, complicates parallel test execution (the very thing TestPodDefaults was built for), and makes "why did my pod land in namespace X?" hard to answer. For an MVP, fewer resolution paths beat flexible ones.

Why this matters for release: every public class/method/annotation that ships is a documented promise. Today roughly a quarter of the promises are unbacked. Cutting them is the cheapest, highest-leverage action available.

C8 — Minikube specifics and naming leak across layers Medium

Beyond C1.4: LocalServicePod hardcodes host.minikube.internal (LocalServicePod.java:53); MinikitCli wraps three binaries (minikit, minikube, kubectl) under one name; the minikit / minikube / testpods profile-name trio (C2) confuses even the in-repo docs (README says minikube start -p minikit). Users will hit this in their first five minutes. Decide the story: either minikit is an implementation detail never surfaced to users, or it's the product name — not both.

C9 — Error-handling inconsistencies Low / Medium

  • ClassCastException thrown as a "no cluster configured" error (BaseManagedPod.java:314).
  • getNamespace() returns null (TODO) instead of Optional/throw (MinikubeCluster.java:157).
  • Mixed exception vocabulary: ClusterException, TestPodStartException, bare RuntimeException, IllegalStateException for equivalent failure classes across strategies.
  • Broad catch (Exception ignored) {} in doStop()/cleanup() — reasonable for teardown, but silent; at minimum log at debug.

For a test library, error messages are the product: a failed start should tell the user what to run next (kubectl -n ns describe pod …). The foundation (e.g. createAndPingClient's "run kubectl cluster-info" hint) shows the right instinct — apply it uniformly.

C10 — JUnit extension lifecycle-ownership ambiguities Medium

  • afterAll unconditionally closes the registry's cluster (TestPodsExtension.java:290) — including a cluster the user constructed in a @RegisterCluster field initializer. Combined with default DESTROY_ON_CLOSE, a user-created profile can be destroyed by the extension. Ownership should follow creation: whoever created it closes it.
  • Extension state lives in instance fields rather than the JUnit ExtensionContext.Store; with @Nested classes or parallel execution the registry/annotation fields can cross-contaminate.
  • Static-field injection via reflection (assignClusterToTestClassStaticField scans for any static K8sCluster field, annotated or not) is more magic than the Testcontainers precedent; surprising for fields the user meant to manage manually.
  • Registry double-registers pods under both registry name and pod.getName() (Registry.java:107–110), so name collisions across those two namespaces silently overwrite.

5. Proposed target architecture

The goal is not a rewrite. The strategy seams (S2) and the fluent API (S1) stay. The change is to (a) cut dead surface, (b) split the cluster abstraction along its three natural responsibilities, (c) make all dependencies point one way, and (d) shrink the pod base class to an orchestrator over the existing seams.

5.1 Artifact layout

Pragmatic note: if splitting Maven modules feels heavy for the MVP, the same decoupling can be achieved inside core first by enforcing one-directional package dependencies (api ← cluster ← runtime ← pods ← junit) with ArchUnit tests, then extracting artifacts later. The package discipline is the point; the artifact split is the enforcement mechanism.

6. The cluster interface split in detail

This answers the review question directly: yes — split the cluster interface into an operational interface (provisioning/lifecycle, per cluster technology) and interaction interfaces (connection + namespace). Three focused types replace the current fat one:

6.1 Sketch of the resulting API

// ---- operational side (per cluster technology, SPI) ----
public interface ClusterProvider extends AutoCloseable {
  ClusterStatus status();
  void start();                         // explicit, not hidden inside "discover"
  K8sCluster connect();                 // fails fast if not reachable
  void close();                         // applies lifecycle policy IF this provider started it
}

// discovery becomes an explicit, side-effect-transparent helper:
public final class Clusters {
  /** Attach to a running cluster; never starts one. */
  public static Optional<K8sCluster> findRunning();
  /** Attach or start the default local cluster (documented: may take minutes). */
  public static K8sCluster attachOrStart(ClusterSpec spec);
}

// ---- interaction side (technology-neutral) ----
public interface K8sCluster extends AutoCloseable {
  KubernetesClient client();
  ExternalAccessStrategy accessStrategy();
  NamespaceManager namespaces();
  <T> Optional<T> capability(Class<T> type);   // ImageLoader, DashboardUi, ...
}

public interface NamespaceManager {
  Namespace create();                    // generated name, owned
  Namespace create(String name);         // owned; throws if exists
  Namespace attach(String name);         // external; never deleted by us
  Optional<Namespace> find(String name);
  void delete(Namespace ns);             // refuses external namespaces
}

Key properties of this shape:

  • Minikube-only features become capabilities (cluster.capability(ImageLoader.class)), removing the instanceof MinikubeImageLoadTarget checks from BaseManagedPod and GenericPod and letting Kind implement image-loading its own way later.
  • No stub methods. Kind/kubeconfig support is a new artifact implementing ClusterProvider — core never changes and never advertises what it can't do.
  • Ownership becomes mechanical: the party that called start() owns the profile; the party that called create() owns the namespace; close() only reaps what its caller owns. This resolves C10's "extension destroys the user's cluster" hazard by construction.
  • ExternalAccessStrategy loses its Pod parameter — it takes (Namespace ns, String serviceName, int port, OptionalInt fixedPort) or a small ServiceRef record, breaking the cluster→pods cycle (C1.2).

7. Slimming the Pod abstraction

Split Pod<SELF> along its natural fault line — the one LocalServicePod already exposes:

InterfaceMembersImplemented by
TestPod (runtime handle — what tests interact with) start(), stop(), isRunning(), isReady(), getName(), getNamespace(), internal/external endpoints, publishProperties(), getReferencedProperties() Everything, including LocalServicePod — no method throws
ContainerizedPod extends TestPod getLogs(…), exec(…), exposed/mapped ports Workload-backed pods only
WorkloadCustomization<SELF> (fluent mixin) withInitContainer, withSidecar, withPodCustomizer, withResources, labels/annotations BaseManagedPod subclasses; not LocalServicePod

And decompose BaseManagedPod by extraction — no behavior change, just homes:

Extracted collaboratorTakes overApprox. lines out
PodRuntimeContext / DefaultsResolverresolveRuntimeDefaults() and the five-way cluster/namespace resolution (also fixes double invocation)~40
PodDiagnosticsbuildDeploymentDetailsReport() + all appendX helpers + env masking; also becomes the "print diagnostics on start failure" feature~250
PodExec (or use client directly)exec()/getLogs() plumbing~90
ImagePreloader via cluster.capability(ImageLoader.class)preloadExternalImageForMinikube, static image caches (state moves onto the cluster/capability instance — no more static IdentityHashMaps)~50

Result: BaseManagedPod ≈ 350–400 lines doing exactly two things — hold fluent configuration and orchestrate WorkloadManager + ServiceManager + WaitStrategy through start/stop. That is a class a contributor can read in one sitting, which is the stated growth goal.

9.1 Definition of "complete" per shipped feature

For the release, propose this bar for every feature in the Keep column:

  1. Unit tests (mock-server where applicable) and at least one integration test that runs green in CI against minikube.
  2. A documented happy path in the user docs, with a copy-pasteable snippet verified by an example test.
  3. Failure modes produce actionable error messages (R6 bar).
  4. No public method that throws UnsupportedOperationException and no TODO in public Javadoc.

10.2 Closing assessment

TestPods does not have a design problem at the concept level — the seams, ownership semantics, and developer-workflow features are better thought out than most pre-release libraries. It has a surface honesty problem (advertising more than works) and a coupling problem (everything reachable from everything). Both are fixable in bounded, low-risk steps, and the fix order matters: delete first, then decouple, then harden. Done in that order, the remaining code is exactly the small, comprehensible, 100%-working library the release motto calls for — with an architecture (SPI + capabilities + one-way dependencies) that can absorb Kind support, more modules, and the catalog vision without another restructuring.
