Class Hierarchy

Template-Method Stack

The package is built as a layered template-method hierarchy. Each layer narrows responsibility:

Pod
User-facing contract — configuration, lifecycle, ports, logs, properties
↓
BaseManagedPod
Shared start/stop workflow, namespace/cluster resolution, pod-spec customization, logs, exec, port mapping
↓
DeploymentPod · StatefulSetPod
Selects workload kind (Deployment vs StatefulSet) and service shape
↓
GenericPod · PostgreSQLPod · KafkaPod · MongoDBPod …
Fills in the main container, lifecycle hooks, and any extra Kubernetes objects
Kubernetes API objects are created by the workload and service manager layer, not directly by pod classes. WorkloadConfig and ServiceConfig carry the data between them.

Start / Stop Flow

BaseManagedPod.start() — Execution Order

  1. Resolve cluster and namespace defaults
  2. Run preStart() if the concrete pod implements PodLifecycleHooks
  3. Build the pod spec
  4. Create the workload resource
  5. Create the service resource
  6. Wait for readiness
  7. Run postStart() if present

Namespace & Cluster Resolution

resolveRuntimeDefaults()

Runtime defaults are sourced from TestPodDefaults and resolved in priority order:

Cluster

  • Explicit cluster on the pod
  • TestPodDefaults.resolveCluster() — thread-local then global

Namespace

  • Explicit namespace object
  • Explicit namespace name — creates or attaches
  • Shared namespace from TestPodDefaults
  • Cluster default namespace
  • Create a new namespace as last resort
TestPodDefaults.resolveNamespaceName() exists but is not called directly by the current BaseManagedPod flow — the priority list above is the actual path.

PostgreSQLPod

  • Main container listens on port 5432; readiness/liveness probes use pg_isready.
  • Persistent storage is a StatefulSet PVC template named data.

Pod Spec Construction

buildPodSpec() — Customization Order

BaseManagedPod.buildPodSpec() always starts with the main container and applies customizations in this fixed order:

  1. Init containers
  2. Sidecars
  3. Resource requests on the first container
  4. Low-level PodSpecBuilder customizers

withInitContainer(…), withSidecar(…), and withPodCustomizer(…) all affect the pod template — not separate Kubernetes resources.

BaseManagedPod.java:891

Container Builder Classes

  • ContainerDefinition — generic container adapter. Holds image, env, command, args, ports, and an optional HTTP readiness probe. Derives a default wait strategy from those settings. Builds a Fabric8 Container via ContainerSpec.
  • ContainerSpec — low-level Fabric8 container builder. Supports ports, env vars, command/args, volume mounts, readiness/liveness/startup probes, resource requests and limits, and arbitrary Fabric8 customizations.
  • ProbeSpec — probe builder supporting TCP, HTTP/HTTPS, and exec probes.
  • InitContainerBuilder / SidecarBuilder — simple facades that each emit a single Fabric8 Container.
